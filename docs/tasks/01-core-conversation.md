# جریان الف: هسته گفتگو (مدیر پروژه + Claude)

این جریان **به کسی واگذار نمی‌شود**، چون `ConversationProcessor` و پوشه `NLU` آن‌قدر به هم وابسته‌اند که دو نفر همزمان رویش تداخل می‌سازند. برای دیگران، این فایل فقط مرجع «چه چیزی از گفتگو قرار است بیاید» است.

## تقسیم بین مدیر پروژه و Claude

| کار | Claude | مدیر پروژه |
|---|---|---|
| منطق Application (پردازنده، کارت، حالت نیمه‌کاره، قانون‌ها) و تستشان | می‌نویسد و اینجا تست می‌کند | بازبینی |
| لایه EF (مخزن گفتگو، پیکربندی)، Redis، کنترلر و مایگریشن | می‌نویسد | build، مایگریشن، اجرای واقعی با SQL و Redis |
| تست دستی روی Swagger و گزارش خطا | | انجام می‌دهد |

(Claude فقط Domain و Application را کامپایل و تست می‌کند. لایه‌های Infrastracture و Api را مدیر پروژه build می‌کند.)

## کارها

### الف۱) ذخیره گفتگو و پیام‌ها (دیتابیس)

- `IConversationRepository`، `ConversationService`.
- endpointها (draft؛ شکل نهایی در Swagger):

| روش | آدرس | کار |
|---|---|---|
| GET | `/api/conversations?page=&pageSize=` | سایدبار: `{ id, title, lastMessageAt }` |
| POST | `/api/conversations` | گفتگوی جدید ← `{ id }` |
| GET | `/api/conversations/{id}/messages?before=&take=` | پیام‌های یک گفتگو (جدیدترین اول) |
| DELETE | `/api/conversations/{id}` | حذف نرم |
| POST | `/api/conversations/{id}/messages` | ارسال پیام ← پاسخ ربات (متن + کارت یا گزینه‌ها) |
| POST | `/api/conversations/{id}/messages/{messageId}/confirm` | تأیید کارت |
| POST | `/api/conversations/{id}/messages/{messageId}/cancel` | لغو کارت |

- **امنیت:** شناسه گفتگو را سرور می‌سازد. هر درخواستی که شناسه می‌فرستد، سرور چک می‌کند آن گفتگو **مال همین کاربر** است (وگرنه `404`).
- `/api/chat` قدیمی حذف می‌شود (فرانت هنوز استفاده نمی‌کند).
- ارسال پیام و تأیید/لغو: `[RequireActiveSubscription]`. خواندن آزاد.

### الف۲) حالت نیمه‌کاره (Redis)

اگر پیام ناقص باشد («علی پرداخت کرد» بدون مبلغ، چک بدون تاریخ یا بدون وضعیت صیاد)، آنچه فهمیده‌ایم در Redis می‌ماند و فقط **قسمت کم** پرسیده می‌شود.

- کلید: `vexora:pending:{userId}:{conversationId}`، انقضا ۳۰ دقیقه (قابل‌تنظیم).
- محتوا: نیت، مشتری (نام یا شناسه)، مبلغ، تاریخ، شماره چک، وضعیت صیاد، و «چه چیزی کم است».
- لغو («لغو»، «انصراف»، «بیخیال») و دستور کامل جدید، حالت را پاک می‌کند (در Application پیاده شده).
- ورود به این جریان از `ConversationProcessor` بازنویسی‌شده است.

### الف۳) کارت تأیید و رسید

وقتی همه چیز کامل شد، ربات یک پیام با `CardState = Pending` ذخیره می‌کند که `PayloadJson`ش کارت است:

```json
{
  "kind": "RegisterPayment",
  "customer": { "id": 12, "name": "علی رضایی", "isNew": false },
  "amount": 500000,
  "amountInWords": "پانصد هزار تومان",
  "date": "2026-10-24T00:00:00",
  "datePersian": "۱۴۰۵/۰۸/۰۲"
}
```

برای چک: `kind: "RegisterCheck"`، `dueDate`، `dueDatePersian`، `checkNumber`، `bankRegistration` (`Registered` یا `NotRegistered`).

- `confirm`: **فقط شناسه پیام** می‌رود. سرور همان چیزی را ثبت می‌کند که خودش ذخیره کرده (آنچه نشان داده شد = آنچه ثبت می‌شود). هر کارت فقط یک‌بار از `Pending` به `Confirmed` می‌رسد؛ تأیید دوباره همان نتیجه قبلی را برمی‌گرداند و **ثبت دوم نمی‌سازد**.
- مشتری جدید داخل همان کارت و همان تراکنش ساخته می‌شود.
- بعد از ثبت، یک پیام **رسید** ذخیره می‌شود: `{ recordType: "Payment"|"Check", recordId, customerName, amount, datePersian, receivedTotalForCustomer }`.
- «برگرداندن» روی رسید، `DELETE` دفتر حساب (جریان ب) را صدا می‌زند، و بعد از موفقیت رسید «برگردانده شد» می‌شود.
- کارت بعد از ۲۴ ساعت `Expired` است.
- ثبت صیاد: اگر در پیام چک نبود، ربات می‌پرسد «چک در سامانه صیاد ثبت شده؟» با دو دکمه (گزینه‌ها در `PayloadJson`).

### الف۴) مشتری یکتا

- نام کامل در هر کسب‌وکار یکتاست (مثل مخاطبین گوشی). تکراری ← `CUSTOMER_ALREADY_EXISTS`.
- اگر نام نوشته‌شده دقیقاً با یک مشتری یکی است همان انتخاب می‌شود (حتی اگر «علی رضایی بنا» هم هست).
- اگر چند شبیه بود، کاربر از بین نام‌های کامل انتخاب می‌کند. هرگز حدسی انتخاب نمی‌شود.
- ساخت مشتری جدید داخل کارت و با علامت «(مشتری جدید)».

### الف۵) شکستن `ConversationProcessor`

چند کلاس کوچک و تست‌پذیر: تحلیل پیام، تکمیل اطلاعات، پیدا کردن مشتری، ساخت کارت، اجرای تأیید. تست‌های قدیمی (Moq) به‌جای رفتار قدیمی، رفتار جدید را می‌سنجند.

### الف۶) راهنمای مشتری‌های اولیه

چون جمله‌های واقعی هنوز نداریم: ربات یک پیام راهنما (`راهنما` یا دکمه) با **۸ الگوی پیشنهادی** و ۴ مثال برای هر کدام می‌دهد («علی رضایی ۵۰۰ هزار تومان داد»، «چک ۲۰ میلیونی از رضا، سررسید ۱۵ آذر»، ...). endpoint `GET /api/conversations/help` همان متن را به‌صورت JSON برمی‌گرداند.

### الف۷) تست پذیرش

فایل `Acceptance/sentences.tsv` (جمله | نوع | مشتری | مبلغ | تاریخ | جهت) و تستی که همه را از خود NLU رد می‌کند. Claude جمله‌ها را می‌سازد؛ هر وقت جمله واقعی رسید اضافه می‌شود.

### الف۸) (نسخه بعد) نسیه

فروش نسیه و بدهی. فعلاً **ثبت جهت `Given` و فروش پشتیبانی نمی‌شود** و ربات صریح رد می‌کند (قبلاً پیاده شد).

## معیار پذیرش

- [ ] «علی پرداخت کرد» ← می‌پرسد مبلغ؛ جواب «۵۰۰ هزار» همان را کامل می‌کند، کارت می‌آید.
- [ ] صفحه رفرش ← همان سؤال یا کارت دوباره دیده می‌شود.
- [ ] هیچ ثبتی بدون زدن «تأیید» انجام نمی‌شود (تست خودکار با سرویس‌های ثبت که اگر صدا زده شوند خطا می‌دهند).
- [ ] دو بار تأیید پشت سر هم ← فقط یک ثبت.
- [ ] کاربر B نمی‌تواند گفتگوی کاربر A را بخواند یا تأیید کند.
- [ ] مشتری هم‌نام: دومی ساخته نمی‌شود، با پیام روشن.
- [ ] ثبت ← «برگرداندن» ← رکورد از لیست‌ها و جمع‌ها حذف می‌شود.
