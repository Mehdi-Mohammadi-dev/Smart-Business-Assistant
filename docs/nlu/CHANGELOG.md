# تاریخچه تغییرات NLU (پرداخت و چک)

هدف: بخش «ثبت پرداخت» و «ثبت چک» را محکم کنیم، بدون افزودن فیچر جدید.

قاعده کار در هر مرحله: **مشکل ← علت ← راه‌حل ← فایل‌ها ← تست‌ها ← محدودیت‌ها**.
اول تست‌ها نوشته می‌شوند و شکست می‌خورند، بعد کد اصلاح می‌شود تا سبز شوند.

## مرحله ۰: شناسه گفتگو سمت سرور (۲۷ مهر ۱۴۰۵)

### مشکل

1. شناسه گفتگو (`conversationId`) را **کلاینت** می‌ساخت و می‌فرستاد. با رفرش صفحه یا عوض شدن مرورگر، شناسه گم می‌شد و گفتگوی نیمه‌کاره در Redis بی‌صاحب می‌ماند.
2. **حفره امنیتی:** کلید Redis فقط `vexora:conversation:{conversationId}` بود. هر کاربر لاگین‌شده با فرستادن شناسه کاربر دیگر می‌توانست گفتگوی او را ادامه بدهد و لیست مشتری‌های او (کاندیداها) را ببیند.
3. `ChatRequestValidator` برای `ChatRequest` نوشته شده بود ولی کنترلر `ChatRequestDto` می‌گرفت، پس اعتبارسنجی پیام هرگز اجرا نمی‌شد.

### راه‌حل

- شناسه گفتگو را **سرور** از کاربر لاگین‌شده می‌سازد: `ConversationIds.ForUser(userId)` ← `user-{userId}`. کلاینت دیگر هیچ شناسه‌ای نمی‌فرستد (و نمی‌تواند عوضش کند).
- بدنه `POST /api/chat` فقط `{ "message": "..." }` است. حالا اعتبارسنجی هم واقعاً اجرا می‌شود.
- دو endpoint جدید:

| Endpoint | کار |
|---|---|
| `GET /api/chat/pending` | اگر گفتگوی نیمه‌کاره‌ای در Redis هست، همان سؤال (و گزینه‌ها) را برمی‌گرداند؛ وگرنه `data: null`. فرانت بعد از رفرش با این، صفحه را بازیابی می‌کند |
| `POST /api/chat/reset` | گفتگوی نیمه‌کاره را پاک می‌کند (دکمه «گفتگوی جدید») |

### تصمیم

هر کاربر **یک** گفتگوی فعال دارد (نه چند گفتگوی همزمان). برای MVP کافی است. اگر بعداً چند گفتگو لازم شد، شناسه را سرور بسازد و در لیست کاربر نگه دارد، نه اینکه کلاینت بفرستد.

### فایل‌ها

| فایل | تغییر |
|---|---|
| `Caching/Conversations/ConversationIds.cs` | **جدید** |
| `Caching/Conversations/Interfaces/IConversationProcessor.cs` + `Implementations/ConversationProcessor.cs` | `GetPendingAsync` و `ResetAsync` |
| `Services/Interfaces/Chats/IChatService.cs` + `Implementations/Chats/ChatService.cs` | `GetPendingAsync` و `ResetAsync` |
| `Api/Contracts/Chats/ChatRequest.cs` | حذف `ConversationId` |
| `Api/Validators/Chats/ChatRequestValidator.cs` | حذف قانون `ConversationId` |
| `Api/Mappers/Chats/ChatMappers.cs` | شناسه را از بیرون می‌گیرد |
| `Api/Controllers/Chats/ChatController.cs` | بازنویسی: `ICurrentUser`، `ChatRequest`، دو endpoint جدید |

### تست‌ها

`NLU/ConversationTests/ConversationPendingTests.cs` (۱۰ تست، بدون Moq): ساخت شناسه، بازیابی هر چهار حالت انتظار، جدا بودن کاربران از هم، و پاک کردن.

### آزمایش دستی

1. با کاربر A بنویس «یک چک ۵۰ میلیونی از رضا گرفتم»، تا سؤال تاریخ بیاید.
2. صفحه را رفرش کن (یا `GET /api/chat/pending` را بزن): باید همان سؤال تاریخ برگردد.
3. با کاربر B لاگین کن و `pending` بزن: باید `data: null` باشد (چیزی از A دیده نشود).
4. `POST /api/chat/reset` بزن و دوباره `pending`: باید `null` شود.

### محدودیت‌ها

- دو پیام همزمان از یک کاربر (دابل‌کلیک) هنوز قفل ندارند (در `ROADMAP.md`).
- `Messages.ConversationIdRequired` دیگر استفاده نمی‌شود (در تمیزکاری حذف می‌شود).

### پیشنهاد کامیت

```

```

## مرحله ۱: استخراج مبلغ

### مشکل (نمونه‌هایی که با کد قدیمی اشتباه ثبت می‌شدند)

| جمله | قبل | بعد |

| دو میلیون و پانصد هزار تومان | ۵۰۰,۰۰۰ | ۲,۵۰۰,۰۰۰ |

| یک میلیون و نیم تومان | (هیچ) | ۱,۵۰۰,۰۰۰ |

| هزار تومان | (هیچ) | ۱,۰۰۰ |
| ۵۰۰ هزار ریال | ۵۰۰,۰۰۰ تومان | ۵۰,۰۰۰ تومان |
| چک ... سررسید ۱۴۰۵/۰۹/۱۵ | ۴ مبلغ (تاریخ هم مبلغ حساب می‌شد) | فقط مبلغ واقعی |

### علت

1. عبارت منظم (regex) مبلغ فقط وقتی کار می‌کرد که کلمه «تومان» یا «ریال» جلوی عدد باشد.
2. لیست اعداد داخل regex ناقص بود (مثلاً «پانصد» بعد از «و» را نمی‌شناخت) و بدون کلمه «تومان»، «هزار» و «میلیون» نادیده گرفته می‌شدند.
3. اعداد تاریخ، شماره چک و مدت («۳ ماه») هم مبلغ حساب می‌شدند.
4. واحد ریال هیچ‌وقت به تومان تبدیل نمی‌شد.

### راه‌حل (نحوه کار جدید)

استخراج مبلغ حالا چهار قدم دارد:

1. **پوشاندن بخش‌هایی که مبلغ نیستند:** تاریخ (`1405/09/15`، `15 آذر`)، مدت (`3 ماه`)، شماره چک (`شماره 123456`)، شماره‌های بلند (صیاد، موبایل). این بخش‌ها با فاصله جایگزین می‌شوند تا جای بقیه متن عوض نشود.
2. **توکن‌بندی:** متن به قطعه‌های «عدد / کلمه عددی / هزار-میلیون-میلیارد / نیم / و / تومان-ریال» تقسیم می‌شود (`MoneyTokens`). شکل‌های چسبیده مثل `500هزارتومان` هم جدا می‌شوند.
3. **پیدا کردن بازه‌ها (span):** دنباله‌های معتبر توکن‌ها با یک دستور زبان ساده. مثلاً «عدد، هزار» معتبر است ولی «عدد، عدد» نه.
4. **انتخاب:**
   - بازه‌ای که واحد پول دارد: اطمینان ۰.۹۸
   - بازه‌ای که هزار/میلیون/میلیارد دارد ولی واحد پول ندارد: اطمینان ۰.۹۰
   - فقط اگر هیچ‌کدام نبود، عدد خالی (مثل `علی 150 داد`): اطمینان ۰.۷۵

محاسبه مقدار در `MoneyParser` انجام می‌شود (ایده: `total` و `current`، با پشتیبانی از «نیم» و عدد اعشاری).

## مرحله ۲: تشخیص نوع پیام و جهت (۳۰ مهر ۱۴۰۵)

### مشکل (نمونه‌های واقعی)

| جمله | قبل | بعد |
|---|---|---|
| علی چکش خرید | ثبت چک (اطمینان ۱۰۰٪) | نامشخص |
| علی به دادگاه رفت | ثبت پرداخت | نامشخص |
| چک سی میلیون تومانی از احمد رضایی دریافت کردم | نامشخص | ثبت چک |
| به علی ۵۰۰ هزار دادم | دریافتی ثبت می‌شد (برعکس) | رد می‌شود با توضیح |
| علی ۵۰۰ هزار گرفت | دریافتی ثبت می‌شد (برعکس) | رد می‌شود با توضیح |
| علی ۵۰۰ هزار تومان کارت به کارت کرد | نامشخص | ثبت دریافتی |
| به علی ۱۰ میلیون جنس دادم | «درخواست شناسایی شد» (با وضعیت موفق، بدون هیچ کاری) | «پشتیبانی نمی‌شود» |
| چک ۵ میلیونی و ۲ میلیون نقد از علی گرفتم | فقط مبلغ اول ثبت می‌شد | از کاربر می‌خواهد جدا بفرستد |

### علت

1. کلمه‌های کلیدی با «شامل بودن» در متن جستجو می‌شدند، نه کلمه کامل («چک» داخل «چکش»، «داد» داخل «دادگاه»).
2. «دریافت کردم» (کلمه پرداخت) با «چک» امتیاز برابر می‌گرفت و نتیجه نامشخص می‌شد، با اینکه جمله چک است.
3. جهت تراکنش (من دادم یا او داد) هیچ‌جا تشخیص داده نمی‌شد و همه‌چیز دریافتی ثبت می‌شد.
4. برای درخواست‌هایی که هنوز پیاده نشده‌اند، پردازنده «شناسایی شد» با وضعیت موفق برمی‌گرداند و هیچ کاری نمی‌کرد (خطای بی‌صدا).
5. اگر پیام دو مبلغ داشت، مبلغ اول بی‌صدا انتخاب می‌شد.

### راه‌حل

- **تطبیق کلمه کامل:** پیام به کلمه‌ها شکسته می‌شود و کلید باید یک یا چند کلمه کامل پشت سر هم باشد (`PhraseMatcher`). «ها» و «های» یکی حساب می‌شوند.
- **اولویت چک:** اگر کلمه «چک» (یا «چکی»، «چکها») هست، رقیب «پرداخت» حذف می‌شود، چون فعل‌های «داد / گرفتم / دریافت کردم» برای چک هم استفاده می‌شوند.
- **تشخیص جهت** (`DirectionDetector`، خروجی `DirectionHint` داخل `NluResult`):
  - دریافتی: داد، گرفتم، دریافت کردم، پرداخت کرد، واریز کرد، بهم داد، کارت به کارت کرد
  - پرداختی: دادم، پرداخت کردم، واریز کردم، **گرفت**، **دریافت کرد** (سوم‌شخص گرفته = من داده‌ام)
  - اگر هر دو یا هیچ‌کدام بود: نامشخص (به‌عنوان دریافتی با کارت تأیید پیش می‌رود)
- **قفل‌های ایمنی در `ConversationProcessor`:**
  - جهت پرداختی ← «در این نسخه فقط دریافتی ثبت می‌شود»
  - بیش از یک مبلغ متفاوت ← «هر ثبت را جدا بفرستید»
  - درخواست پشتیبانی‌نشده ← «در نسخه فعلی پشتیبانی نمی‌شود» (وضعیت ناموفق)

### تصمیم‌ها

| تصمیم | دلیل |
|---|---|
| «گرفت / دریافت کرد» (سوم‌شخص) = پرداختی و رد می‌شود | امن‌تر است که رد کنیم تا اشتباه ثبت کنیم |
| جهت نامشخص = دریافتی | نسخه ۱ فقط دریافتی دارد و کارت تأیید جهت را نشان می‌دهد |
| دو مبلغ مساوی یک مبلغ حساب می‌شود | «چک ۱۰ میلیونی به مبلغ ۱۰ میلیون» یک مبلغ است |
